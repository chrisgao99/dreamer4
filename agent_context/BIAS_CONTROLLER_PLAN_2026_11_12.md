# 学习式 bias 控制器：用闭环结果训练"调 bias 的旋钮"（2026-11-12，已与用户确认）

> **本文件是 `dreamer4/agent_context/ROW_PAIR_ORDER_Z_WM_FINETUNE_PLAN_2026_11_09.md`（下称"原方案"）的改进版计划。**
>
> - 原方案用日志里的通行顺序 z 生成 attention bias，再用日志轨迹的 flow loss 训练。实验 1（1a）和 1b-v2 都表明这条路控制不了通行顺序，结果见第 1 节和原方案 §8.8。
> - 本方案保留"用 attention bias 调节两车交互"这个通道，但换掉信号来源和训练目标：bias 由模型自己的计划算出的冲突决定，用闭环 rollout 的结果（碰撞、卡住、偏离日志）来训练。
> - 路径约定同原方案：文中路径都相对于 `tri30/`。

## 0. 一句话

- **出发点：** 手动给冲突车对的 attention bias 加 δ，能把碰撞从 0.81 降到 0.10。
- **要做的：** 训练一个小网络，在每次重规划时自动决定给哪对车加多少 δ。
- **输入：** 模型自己这一轮的草稿计划里算出的冲突信息，不依赖日志。
- **训练目标：** 闭环 rollout 的结果，不是日志似然。

## 1. 为什么改：原方案的结果

### 1.1 实验 1（1a）：冻结 85k，只训练 g（详见原方案 §8.8）

- **碰撞几乎不降：** 有标签车对的碰撞从 7.3% 降到 6.9%，不显著。
- **反转 z 也翻转不了顺序：** 有冲突时按日志顺序通过的比例，unknown 84.4%，oracle 和 reversed 都是 84.6%。
- **g 学到的 bias 大多与方向无关：** 平均 1.6 个单位与方向无关，随方向变化的部分只有 0.8。
- **bias 很大，attention 也被改了很多，行为却不跟方向走：** 让行车对优先车的 attention 中位数降了约 5 倍。

### 1.2 实验 1b-v2：z 更密集，解冻去噪器，loss 集中在有 z 的车上（2026-11-11）

- **做法：**
  - 标签 v2 加入同向车对和一开始就在重叠段的车对。训练集车对从 1.7 万增到 41.5 万，第 10 帧时 z 开着的车对从每样本约 0.36 增到 2.3。
  - 解冻去噪器（lr 1e-5），z-dropout 0.3，有 z 的车 loss 权重 1、其他车 0.1，训练 1 万步。
  - 运行目录是 `dreamer4/waymo/pair_order_z/runs/exp1b_v2_dense_z_20261111/`。
- **结果：**
  - **控制力为 0：** 开始时 z 开着、顺序还没定的 339 对里，冲突中反序通过的比例是 unknown 10.1%、oracle 10.0%、reversed 10.5%。场景配对 bootstrap 的差值约等于 0。
  - **z 能降碰撞，但不分方向：** 场景碰撞率 oracle −1.28 pt（95% CI [−1.75, −0.84]），reversed −0.93 pt（[−1.35, −0.51]），两者都显著，且方向相同。
  - **微调本身让模型变得更爱走。** 下表是同一模型在 unknown 下与冻结 85k 的对比（种子不同，只比总体）：

    | 指标 | 冻结 85k | 1b-v2 unknown |
    |---|---|---|
    | ADE | 2.47 | 2.14 |
    | 一直不起步 | 37.6% | 26.1% |
    | 场景碰撞率 | 41.3% | 51.4% |
    | 同向车辆碰撞（占全部场景-rollout） | 18% | 29% |

    没有做"同样微调但不给 z"的对照，所以分不清这个变化来自 z 还是训练方式。
  - **训练信号仍然很弱：** 真值 z 带来的 flow loss 下降，有 z 的车 0.24%，交叉车对约 0.5%。
- **6062–2310 场景：** unknown 56%，oracle 59%，reversed 56%，没有效果。

### 1.3 根本原因

- **日志里几乎没有"z 和场景不一致"的样本。** 通行顺序基本能从场景推断出来，所以 teacher-forced 的 flow loss 不需要 z，模型也就学不会在两者冲突时听 z 的。换 z 的输入方式（token、FiLM、value 边特征）不能改变这一点。
- **出错的情况很少，而且训练里从没见过错误的后果。** 日志里没有碰撞；"早起步 1 s"在 40 步 flow loss 里只是很小一项误差，闭环里却会撞车。
- **信息其实是够的。** 模型的输入加上 RelativeAgentBias 已经包含了足够的信息，缺的是一个在"会撞"时把行为拧对的机制。

### 1.4 仍然成立的证据：手动 steering（`wm_interaction_probe/results/bias_steer/`，原方案 §1）

场景是 95720e9471028705:6062（ego 6062，冲突车 2310），MoN `best_ade.pt`，128 个配对 rollout：

| 设置 | ego–2310 碰撞 |
|---|---|
| 不加 | 0.81 |
| ego→2310 +2，全部三处 | 0.45 |
| ego→2310 +2，只加 agent_attn | 0.66 |
| ego→2310 +4，全部三处 | 0.38 |
| ego→2310 +4，只加 agent_attn | 0.43 |
| ego→2310 +2，2310→ego +4（combo `ego2_oth4`） | 0.10，但 ego 一直不起步 25% |
| 对照：ego→2310 +2，2310 → 一辆停着的车 +4（`ego2_oth4ctrl`） | 0.23 |

- **"全部三处"：** 场景编码器的 agent 自注意力（4 层）、去噪器 agent_attn（8 层）、scene_cross 的 agent 部分。8 个 head 都加，每次重规划都加。
- **结论：** bias 是有效的旋钮，而且要三处都加。
- **对照组的含义：** 给一辆无关的车加 bias 也能降碰撞，说明 δ 有一部分作用是"让这辆车整体更谨慎"，而不只是"让那辆车"。训练时必须约束这一点，否则会学成让所有车都慢下来。
- **其他：** ≥3–4 logit 时会变成对任何车都冻结；在原方案的 1a、1b 里 g 只加在 agent_attn 上，比三处都加弱。

## 2. 新设计

### 2.1 每次重规划的推理流程

1. **草稿：** 用这一轮抽到的噪声 x0，不加 δ，采一份 4 s 的联合计划。
2. **算冲突特征：** 从草稿里找出可能冲突的车对，算出每个有向车对 i→j 的特征（见 2.2）。
3. **控制器输出 δ：** 对每对冲突车给出 δ_{i→j} 和 δ_{j→i}。
4. **正式计划：** 用**同一个 x0**、加上 δ 再采一次，执行前 5 步。

### 2.2 随机性（上一轮和这一轮的计划可能不同）

- **不用上一轮的计划。** 每一轮都用这一轮自己的草稿。
- **为什么同一个 x0 能解决问题：**
  - 给定噪声后，flow 的采样过程是确定的，走哪个模式（左转还是直行）主要由 x0 决定。
  - 所以草稿和正式计划处在同一个模式里，除非 δ 本身改变了决策，而这正是想要的。
  - 特征描述的是"这一轮如果不干预会发生什么"。
- **下一轮换了模式**（比如从左转变成直行）：新的草稿会跟着变，特征和 δ 也一起重算。
- **δ 在相邻两轮之间跳变：** 加滞回，触发后至少保持 N 轮；或者对 δ 做平滑。
- **代价：** 每轮采样两次，评估时间约翻倍。草稿可以只用 4 个 solver 步。
- **扩展：** 用 M 份不同噪声的草稿，把特征换成概率（比如冲突概率、Δt 的分布），表达"对方可能左转也可能直行"。第一版只用 1 份草稿。

### 2.3 输入（每个可能冲突的有向车对 i→j，约 20 个数）

| 类别 | 特征 |
|---|---|
| 当前状态 | j 在 i 坐标系下的 dx、dy；航向差的 sin/cos；距离；两车速度 |
| 草稿里的冲突 | 两条规划路径是否交叉；各自到达冲突点的时间 t_i、t_j 和 Δt（隐含谁先、先多少）；各自离冲突点的距离；同一时刻的最近距离及发生时间；按碰撞方框预测是否会撞、几秒后撞；冲突点处的航向差（交叉、对向、同向） |
| 场景上下文（第二版） | 场景编码器给 i、j 的 agent token（256 维，先投影到 32 维），带入地图、灯态、路权 |

- **门控：** 草稿里路径不交叉、又离得远的车对，δ = 0，不经过网络。
- **不依赖日志：** 部署时可用。同向跟车、rollout 里新出现的冲突（日志里没有）都能覆盖。行人和自行车也可以纳入，因为冲突检测本身不分类型。

### 2.4 网络

- **第一版：** 逐车对的 MLP，约 20 维输入，结构 128 → 128 → 输出。最后一层零初始化，训练开始时对模型没有影响。
- i→j 和 j→i 用同一个网络，输入按各自的视角计算。
- 第二版拼入 agent token；如果发现多车互相牵制，再在冲突车对之间加一层小注意力。
- WM 冻结。草稿和特征都在 no_grad 下计算。

### 2.5 输出

- **形式：** 每个冲突车对两个标量 δ_{i→j} 和 δ_{j→i}，8 个 head 共用，所有层、所有 flow 步共用，每轮重规划算一次。范围约 ±4（tanh 限幅）。
- **加在哪里：** 和手动 steering 一样，三处都加：编码器 agent 自注意力、去噪器 agent_attn、scene_cross 的 agent 部分。可以直接复用 `wm_interaction_probe/bias_steer.py` 的 `BiasSteer`。加到编码器的话，正式计划要重新编码一次。
- **为什么先不分 head：**
  - 两个标量就是已经验证过有效的旋钮；
  - 维度低，可以网格搜索得到训练标签；
  - 每个 head 分开调，留到用梯度训练时再做。

## 3. 训练

### 3.1 标签

| 草稿 / rollout 的情况 | δ 标签 |
|---|---|
| 草稿里没有冲突 | 0（门控关掉，不进训练） |
| 草稿里有冲突，原模型跑下去没撞 | **0**。重要的负样本：模型本来就对，不该干预 |
| 草稿里有冲突，跑下去撞了（去掉 3.3 里的误报） | 搜索出的最优 δ |

### 3.2 搜索（离线做一次，存成数据集，不在每个训练步做）

1. **跑原模型：** 在一批训练场景上，每个场景用一份噪声跑原模型，记录草稿冲突和最终是否碰撞。
2. **只对撞了的"场景 × 噪声"搜索：** 对撞车的那对车，试 (δ_{i→j}, δ_{j→i}) ∈ {0, 2, 4}² 的 8 种非零组合，用同一份噪声重跑。结果只由 δ 决定，可以严格配对比较；标签和草稿特征来自同一份噪声，两者对得上。
3. **打分：** 这对车是否碰撞 + 是否撞到别人 + λ·（任一车卡住）+ μ·（两车 ADE 比原模型增加的米数）。选分数最低的组合；分数接近时选 δ 小的。上限测试默认 λ = 1，μ = 0.05/m。
4. **生成标签：** 这次 rollout 里，草稿判定这对车有冲突的那几轮重规划，标签都是选中的 δ；其余轮次为 0。

**省时间：**
- δ 开启之前的 rollout 和原模型完全一样，所以从第一次检测到冲突的那一轮开始分叉即可。
- 冲突解决后（两车都通过、再过约 2 s）提前停止。
- 估算：约 2 万个训练场景跑原模型约 3.5 h，对几千个碰撞情况搜索约 4–7 h。

### 3.3 碰撞的口径

碰撞检测用固定方框：机动车 4.8 × 2.0 m，行人 0.8 × 0.8 m，自行车 2.0 × 0.8 m，不是真实尺寸。在 512 个评估场景的真实日志上，它就会报碰撞：
- 95 个场景（18.6%）的日志里有这种重叠，共 225 对。按类型分：行人–行人 63%，行人–车 25%，车–车 12%。
- 车–车那部分里，78% 是停着或排队的车。它们中心距中位数 4.5 m，真实车长中位数 4.44 m，都小于方框长度 4.8 m。

因此：
- **"真实碰撞"** = 方框重叠，且同一对车在日志里没有重叠过，并且在 rollout 第一步也没有重叠。
- 基线里这类误报占碰撞车对的约 45%（上限估计）。它们不进训练目标，评估时和常规 proxy 口径分开报告。

### 3.4 迭代（DAgger）

控制器接入后，车的行为会变，可能出现新的冲突。所以：带着控制器再跑一遍；只对仍然碰撞的情况重新搜索，加入数据集；重新训练。预计一两轮就够。

### 3.5 备选的训练方式

- **通过 rollout 反传梯度：** WM 冻结，只训练控制器，损失是可导的碰撞间隙、卡住、偏离日志。不需要标签，可以借用 MoN 的 80 步 unroll 代码（`train_mon80_ddp.py`）。显存大，碰撞梯度只在两车靠近时才有。适合在搜索版跑通之后做精调，也可以借此改成每个 head 分开调。
- **规则老师：** 例如"草稿里晚到的车对早到的车 +2，早到的车对晚到的车 +4"，直接照搬手动结果。可以作为初始化或对照。

### 3.6 风险

- **学成"让所有车都慢下来"：** 1.4 里的对照组已经暗示了这种可能。靠卡住惩罚、ADE 惩罚和"没撞的冲突标签为 0"来约束。
- **一直不起步：** combo 那组 ego 有 25% 不起步，必须作为指标和代价项。
- **误报污染：** 按 3.3 的口径排除。
- **计算量：** 推理翻倍。
- **控制范围：** 冲突检测依赖草稿，草稿里没出现的冲突（比如另一辆车突然抢行）管不到。这和原方案 §8.1 第 4 点一样，需要以后的干预训练（原方案 §3.6）来补。

## 4. 执行步骤

1. **上限测试（2026-11-12 开始运行）**
   - 代码 `dreamer4/waymo/pair_order_z/bias_ceiling.py`，输出 `dreamer4/waymo/pair_order_z/runs/bias_ceiling_85k_20261112/`。
   - 设置：冻结 85k，512 个评估场景，评估协议同原方案 8.3（EMA、generate-all、80 步、commitment 5、8 个 solver 步、fp32）。每个场景 K = 8 个 rollout，共用一个种子，所以各条件之间配对。
   - 每个场景：
     1. 先跑原模型，找出真实碰撞次数最多的车对（不含行人–行人）。
     2. 对这对车搜索 (δ_{q→k}, δ_{k→q}) ∈ {0, 2, 4}²，三处都加、8 个 head 都加、每轮都加（`BiasSteer`）。
   - 报告：
     - 原模型；
     - 按场景选的上限（每个场景一组固定 δ）；
     - 按 rollout 选的上限（每份噪声各自最优，对应"读得懂草稿的完美控制器"）；
     - 每一组固定 δ 全局使用的效果；
     - 按车对类型（交叉、同向、行人或自行车）分开。
   - 指标：真实碰撞、proxy 碰撞、目标车对碰撞、其他车碰撞、两车卡住和不起步、两车和全场景的 ADE。
   - 每个场景的结果单独存成 npz，可以断点续跑；`--summarize_only` 可以换 λ、μ 重新统计。
   - **判定（预先写定）：**
     - 按场景选的上限能让目标场景的真实碰撞相对下降 ≥ 50%，同时卡住增加 ≤ 5 pt、两车 ADE 增加 ≤ 20%：这个旋钮值得学，进入第 2 步。
     - 相对下降 < 20%：bias 只对少数场景有效，先换方向（例如 §3.6 的干预训练、碰撞损失、MoN 挑选）。
     - 介于两者之间：看按类型分开的结果，只对有效的类型做。
2. **实现草稿和特征，并检查一致性。** 在 δ = 0 时，正式计划必须和草稿逐位相同；再测加 δ 后正式计划和草稿处在同一模式的比例。
3. **生成训练标签**（3.1–3.2），在训练场景上进行，评估场景不参与。
4. **训练控制器，然后评估。** 512 场景、K = 32，指标同第 5 节，并跑三个 steering 场景（原方案 §5）。
5. **DAgger 一两轮**（3.4），然后视需要用梯度精调（3.5）。
6. **以后：**
   - 把原方案的 z（预测的"谁先过"）作为控制器的一个输入，作用是协调：两车共用一个决定，从构造上避免两车都走。
   - 补上行人和自行车的冲突。

## 5. 评估

- **碰撞：** 真实碰撞（3.3 的口径）和常规 proxy 碰撞都报；场景-rollout 率、agent-time 率；按类型拆分（复用 `collision_breakdown.py`）。
- **副作用：** 一直不起步、后 4 s 卡住、rollout 和日志路径长度之比、ADE、minADE、offroad。
- **控制器本身：** 触发的比例（多少车对、多少轮重规划给了非 0 的 δ）、δ 的分布、没撞的冲突上是否保持为 0。
- **统计：** 场景配对 bootstrap，所有条件用同一组种子。

## 6. 与原方案的关系

- **放弃：** 用日志 z 做 teacher forcing 作为主要训练信号；只加在 agent_attn 上的 bias。
- **保留并复用：**
  - 注入钩子：`chunk_bias` 和 `BiasSteer`；
  - 评估流水线：`eval_zbias.py`、`eval_zbias_v2.py`、`summarize_*.py`、`collision_breakdown.py`；

  - 场景测试：`scene_test_1a.py`、`render_scene_test.py`。
- **原方案中仍有效的部分：** 对 z 的分析（§2、§3.5）留作"协调变量"的后续输入；干预训练（§3.6）仍然是处理"对方意外动作"的必要补充。
