# 用"谁先过"变量 z 改进 WM 的交互：方案（2026-11-09，已与用户确认，尚未实现）

本方案的目标是改进 world model 在细节交互上的表现：减少碰撞，让通行顺序符合路权，并让车对对方的实际运动做出反应。做法是把"每对冲突车谁先过"做成 WM 内部一个有监督的 pair 变量 z，再把 z 变成去噪器 agent_attn 的 bias。小模型（pair head）先单独训练，再接入 WM。

> **2026-11-12 更新**：改进版计划见 `dreamer4/agent_context/BIAS_CONTROLLER_PLAN_2026_11_12.md`。它改为训练一个 bias 控制器：输入是模型自己的草稿计划算出的冲突，训练目标是闭环结果。实验 1b-v2 的结果也记录在那里。
>
> **2026-11-11 更新**：实验 1（oracle z，冻结 85k，只训练 g）已完成，结果为阴性：oracle z 几乎不降碰撞，反转 z 也翻转不了通行顺序。结果、碰撞来源，以及"为什么只有很少一部分车对有 z"见第 8.8 节。
>
> **2026-11-10 更新**：新增第 8 节"WM 初版实验计划"，第一轮 WM 实验按第 8 节执行（finetune，不从头训练；起点是 MoN 之前的 stage 1 `best.pt`（85k）；先用 oracle z 冻结 WM 只训练 z→bias）。第 8.1 节汇总了小模型实验（rowz pilot / v2 / v3）对本方案的修改。
>
> **路径约定**：文中所有路径都相对于 `tri30/`（另一台服务器上 `tri30/` 之后的路径相同）。注意各 checkpoint 的 `config.json` 里存的是本机绝对路径，换服务器时要用命令行参数覆盖。

## 1. 背景：为什么要改 representation，不是挑样本

**目标模型**：`dreamer4/waymo/checkpoints/waymo_daf_laneconn90k_mon8_gt_unroll80_b5_detach0_10k_20261009/best_ade.pt`（MoN step 9500）。

- 结构：
  - 11 帧（1.1 s）历史；
  - 一次生成 40 步联合动作 (a_lon, a_lat, Δyaw)，执行 5 步后重规划；
  - 每次重规划 8 个 flow 步。
- 训练：`physical=False`，所以没有碰撞损失，`collision_weight=0.1` 并没有生效。
- 表现：
  - 轨迹看起来真实，能复现日志，也有足够的随机性；
  - 但部分场景的碰撞率达到 50–80%，重采样多少次都一样。

**已有证据**（细节见 `dreamer4/agent_context/RELATIVE_AGENT_BIAS_ATTENTION_ANALYSIS_2026_11_05.md` §5、§10、§11，以及 `wm_interaction_probe/`）：

- **决策在 t0 的快照上就定了，之后不看对方怎么动。** 例如 ego 何时起步，由 t0 时冲突车的位置和速度决定。
  - 单条 rollout 内，起步时间与对方实际运动的相关约为 0。
  - ego 从不等冲突区清空。
- **两车没有协调。** opposing 场景里，联合采样的首个规划碰撞率是 79%，打乱配对后是 77%。
- **RelativeAgentBias 只用位姿，没有速度和时间。** 冲突车分到的 attention 约为 1/N。
- **steering 说明 attention bias 可以当"让行信号"用**（推理时手工加 δ；做法见第 3.6 节）：
  - ego→2310 +2 logit：ego 只对 2310 等待；加在无关车上没有效果。
  - 两侧都加：碰撞从 0.81 降到 0.10。
  - ≥3–4 logit：变成对任何车都冻结。
  - 量级大约是 +1 ≈ 多等 1 s，+2 ≈ 多等 3 s。
  - 合适的 δ 因场景而异：让停着的车让行 +2 就够，正在转弯的车要 +4。
  - 碰撞下限约 0.38，来自 2310 左转切得太狠。这是路径问题，z 修不了。
- **不能用 attention 统计量作目标。** 在 t0，撞和不撞的 rollout attention 相同（AUC 0.53）；之后撞的 rollout attention 反而更高，那是两车靠近的后果。
- **按违规挑 MoN 赢家没有用**（`waymo_daf_laneconn85k_mon8_select_{ade,constrained}_unroll80_b5_detach0_20261106`）：
  - 约 8.7k 步时，B 的 ADE 和 A 相同；
  - 同批次配对比较，B 的候选碰撞反而多约 7%。
  - 原因是日志本身没有碰撞，两种挑法的赢家都接近日志，梯度只是把赢家往日志拉，撞车的样本拿不到梯度。挑样本本质上就是换了权重的 BC。
- **BC 学不会交互的可能原因**：
  - 在 40 步的 flow loss 里，"晚 1 s 起步"只占很小一部分误差；
  - flow 可以把"走"和"等"都保留成模式，却不需要把选哪个和对方的状态联系起来。
  - 所以 80% 碰撞的场景里，"走"这个模式的概率本身就是错的。

**路权与通行顺序数据**：`waymo_interaction_screening/results/row_audit_step0_v5_20261105/`（SUMMARY.md、analysis/、pairs/）。

- 规模：421,825 对，2,331,398 行（pair × 时刻）。
- t0 路口、路权已知：train + val 共 85,580 对。
- 规则一（没空档时非路权方让）：各类型都成立，98.6–99.8%。
- 规则二（有空档时非路权方走）：成立比例依类型 36–92%。
- 准确率（validation）：
  - 匀速到达顺序 0.911；
  - MLP（距离 + 速度）0.952，困难子集 0.869；
  - MLP 加路权 0.969，困难子集 0.931。
- 本方案讨论时补算的数字（t0、路口、路权已知，含 test，n = 90,151）：
  - 非路权方没空档却先过（"抢行"）：只有 585 对，其中 550 对路权方确实减速了。
  - contested pair 里，第二辆车从 t0 起进入冲突区的时间中位数是 6.0 s，p75 7.0 s，比 4 s 的规划窗口长。
  - 各类型的量足够跨场景学习，例如无控制左转 12,507 对，许可左转（一方灯态）12,198 对。

## 2. z 的定义与真值

- **冲突对**：沿用审计的定义（`row_audit_extract.py` 的 `pair_rows`）。
  - 两车日志路径有空间重叠就算，判据是中心距 < 两车半宽之和 + 0.5 m，不要求同时到。
  - 每车第一次进入重叠区的帧是它的进入帧，早的为先。
  - 第 5 帧前已在冲突区的对（`pre_existing`）去掉，同帧进入的对（`tie`）也去掉。
- **类别**：z_ij ∈ {i 先, j 先, 无冲突}。z 由两车共用，并且是反对称的。
- **每次重规划在时刻 t 重给标签**：
  - 两车都还没进入：按日志里的先后。
  - 先过的车还在冲突区里：仍标"它先"，让行信号保持到冲突区清空。
  - 先过的车已经离开：标"无冲突"。
- 注意："无冲突"这一类也透露了路线（例如对方右转而不是左转）。把 z 当潜变量可以接受，但 head 必须能从历史和路线里预测它。
- 训练时刻要在接近过程中均匀采样。不要用 L10/L20 这种从进入时刻往前倒推的锚点，它们会泄露时间。

## 3. 设计

### 3.1 pair head（单独训练的"小模型"）

- **输入**：
  - 两车的 agent 表示；
  - 显式 pair 特征：相对位姿和速度、到冲突点的距离和时间、lane graph 上的冲突关系、路权 r_ij（有、无、未知）加类型 embedding，以及对方是否已在冲突区里。
- **输出**：p(z_ij)，用交叉熵训练。
- **结构要求**：以紧凑的 pair 特征为主，容量小。这样它靠结构跨场景泛化，而不是记住某个路口（见 3.5）。
- **路权未知的对**（路口 pair 的约 42%）：r=0，不要丢掉。训练时再随机把一部分 r 置为未知，避免模型过度依赖标签。

### 3.2 z → bias：bias 没有单独的目标

- **形式**：b_ij^h = g(z_ij, pair 特征)，每个 head 一个数。
  - 用 `3·tanh` 限幅；
  - **零初始化**，训练第 0 步与原 WM 完全一样；
  - 只加在去噪器的 agent_attn 上。scene_cross 在 δ 大时会挤掉地图 key，所以不加。
- **训练目标**：就是 WM 原有的 flow loss，拟合日志轨迹，训练时把真值 z 喂进去（teacher forcing）。
  - 梯度回答的问题是："已知对方先过，bias 取多大能让日志轨迹的似然最大"。
  - 所以 bias 的大小按场景学：g 的输入有 pair 特征，同样是"对方先"，停着的车和正在转弯的车可以得到不同的 bias。
  - bias 太大也会受罚：车等太久就与日志不符，flow loss 会把它压回去。固定 δ 时出现的"ego 一直不起步"，在这里直接是损失。
  - WM 本来就对的场景：知道 z 几乎没有新信息，梯度很小，g 只需要不破坏原来的行为。
- **z-dropout**：一部分样本把 z 置为"未知"。
  - 这提供了一个无条件模式，供推理时第一次采样（见 3.4）。
  - 每个场景的 loss(真值 z) − loss(z 未知)，就是"知道谁先过"的信息量。它可以直接显示哪些场景在被改、改了多少。
- **flow loss 里只能用真值 z 或"未知"，不能用 head 预测错的 z。** 否则日志和 z 互相矛盾，WM 会学会忽略 z。head 的错误由它自己的 CE 和校准来管。
- **闭环 unroll 训练时**：rollout 一旦明显偏离日志，日志里的先后可能不再成立。这些重规划改用"未知"。
- **训练顺序**：先只训练 g 和 pair head，WM 本体冻住，然后再用小学习率解冻去噪器。

### 3.3 为什么这样能改 representation

- 通行顺序标签来自日志，不依赖 WM 的样本，所以在 80% 碰撞的场景里同样有效。
- pair head 的 CE 梯度进入编码器，逼它把"谁该先走"分开。
- dynbias 的教训是：只加特征、没有对应的训练信号，模型就不用。CE 和 teacher-forced 的 flow loss 就是这个训练信号。

### 3.4 推理

1. 每次重规划时，先有路线，再算 r 和 z，最后由 g 给 bias 并生成计划。
   - 第一次重规划：先用 z=未知 采一次计划，取每辆车的路线，算出 r 和 z，再带 bias 采正式计划。
   - 之后每次：用上一次计划剩下的 35 步当路线。
2. z 由 head 采样，每对车只采一个，两车共用。这样从构造上就不会两车都走。
3. 重算 p(z) 时加滞后：变化足够大才换 z，避免来回翻。对面抢行时 p(z) 会翻过来，这就是"反应"。
4. 路权标注器本身就是"路径 + 地图 + 灯态"的函数，可以直接跑在 WM 的计划上。因为推理时的路线来自 WM 计划，比日志路线更噪，训练时要给路线加噪。

### 3.5 日志之外的分支（例如日志里 A 直行，rollout 里 A 左转，路权随之改变）

单纯用日志监督保证不了这些分支，有两个缺口要补：

1. **同一场景的其他分支没有标签，只能靠跨场景泛化。**
   - head 监督的是一个函数：(两车路线, 状态, 路权) → 谁先过。"A 左转、对向直行车有路权"在别的场景的日志里出现过上万次。
   - 前提一：z 和 r 必须按这个分支自己的路线重算（见 3.4）。否则两个分支输入相同，z 不可能不同；z 按日志路线采、WM 却走另一条路线时，两者还会互相矛盾。
   - 前提二：head 不能记住场景（见 3.1）。
2. **WM 会走到日志里没有的状态**：两车都蹭进冲突区、距离已经很近、路径切得太狠。日志里险情极少，这是 BC 典型的分布偏移。做法类似 DAgger，在 WM 自己的 rollout 上加不依赖日志的标签：
   - 已在冲突区里的车就是先过的车（按定义）；
   - 没空档（margin_N ≤ 0）而且停得下：非路权方让，98.6–99.8%；
   - 停不下（需要的减速度 > 3 m/s²，即两条规则里拟合出的 A=3）：这辆车先过。
   - 规则判断不了的，用 head 自己的预测。
   - 用这些标签训练 head，并把 z 喂给 g。这些分支上 g 没有轨迹目标，但有两个不需要日志的损失：碰撞损失，以及 rollout 实际的先后顺序与 z 一致。
   - 有空档、规则二只有 36–92% 成立的格子，本来就没有确定答案，只用 head 从日志里学到的概率，不给硬标签。

### 3.6 干预训练（补上日志里没有的"对方意外动作"）

- 做法：把一辆车的日志未来沿它自己的路径整体提前或推后 0.5–3 s（"错时"），作为强制执行的车。
- 其余车的目标：
  - 碰撞损失；
  - 扰动后由 head 或规则给出的通行顺序；
  - 离冲突远的车贴近原模型。
- 这样"对面抢行了也得躲"有了明确的目标。如果只有"别撞"，模型会学成 steering 里看到的那种无差别减速。

steering 当时的加法，供对照：
- 8 s rollout 的 16 次重规划都加同一个常数 δ。每次重规划里，bias 只算一次，所有层（4 层编码器、8 层去噪器 agent_attn、scene_cross）和 8 个 flow 步共用。
- gated 版本只在两车仍在接近时才加（最后 0.1 s 内距离缩小 > 0.02 m）。碰撞同样低（0.10 和 0.06），"ego 一直不起步"减半（0.25→0.12，0.36→0.15）。
- 学出来的 g 相当于把这个开关变成连续的：z 变为"无冲突"或对方离开后，bias 自然关掉。

## 4. 执行步骤

> 2026-11-10：第一轮改按第 8 节执行。第 8 节的实验 1 对应这里的第 3 步（但用 oracle z、不需要 head），实验 2 对应第 2 步的 A2。第 0 步的分格可以用实验 1 的结果近似（见 8.3）；第 1 步的路权与 v5.1 推迟。

0. **WM 失败分格表**（只需推理）。
   - 在 ROW 已知的 pair 上采样 WM，并存下样本。
   - 按"路权类型 × margin_N"分格，统计碰撞率和 P(N 先过)，与 SUMMARY 表对比。
   - 把碰撞分成三类：顺序没定（协调问题，z 能修）、顺序定了但间隔太短（执行问题）、路径切得太狠（路径问题，z 修不了）。三类的比例决定第 3–5 步的比重。
1. **标签。**
   - 先做 v5.1：约 10% 的 signal_red_partial pair 在冲突前红灯变绿，这些标为未知。
   - 在每个训练时刻重算路权和 z。
   - 按 scenario_id + track id 对接到 WM 数据（50k ooi_centered 或全量 scene cache）。不能按 shard 顺序对接。
2. **单独训练 pair head**，输入与 WM 一致（1.1 s 历史、WM 的地图和灯态、每 0.5 s 一个时刻），做两版：
   - A1：自己的小编码器加显式 pair 特征；
   - A2：同样的 head，但读冻结的 best_ade.pt 编码器 token。
   - A2 明显不如 A1：信息不在 representation 里，需要第 3 步用 CE 改编码器。
   - A2 ≈ A1：信息在，只是没被用上，主要靠 bias 通道。steering 的结论偏向这一种，但只看了一个场景。
   - 参照值：MLP 加路权在 t0 困难子集上 0.931。还要检查校准是否能复现 SUMMARY 表。
3. **接入 WM，WM 冻住**：pair head 加 CE，g 加 z-dropout，用 teacher-forced z 的 flow loss 训练。用 `bias_effect.py` 确认冲突 pair 上的 bias 在 2 logit 左右，不到 4。
4. **小学习率解冻去噪器**，加 DAgger 式规则标签、z 一致性损失和碰撞损失。
5. **加错时干预训练。** 需要的话，再在所有候选上加碰撞损失或 flow-DPO（mon-select 的结论也指向这一步）。有了 z 的约束，不容易学成无差别冻结。

## 5. 评估

- 512 场景 eval：ADE、minADE、CPD、碰撞率。还要看"ego 一直不起步"和冻结车辆的比例，防止碰撞下降只是因为车不走了。
- 三个 steering 场景，用同样的配对种子：95720e9471028705:6062、3a99d1ec2d955550:619、47e836ed96e19bda:1275。
- 第 0 步的分格表在训练后重做：
  - margin_N < −1 的格子应接近 0%（日志 0–2%）；
  - 有空档的格子应接近日志的比例；
  - 按路线分组（例如 A 直行和 A 左转的 rollout），分别看碰撞率和先后顺序是否符合各自的路权。
- head 本身：通行顺序的准确率和校准，在日志状态和 WM 状态上分开报告。
- z-dropout 的信息量分布：哪些场景依赖 z。

## 6. 风险与未决事项

- head 预测错的 z 会被 WM 执行。这只能靠 head 的校准，以及重规划时重新评估来纠正。
- 路线噪声：推理时的路线来自 WM 计划，与训练用的日志路线有偏移。
- 路径切得太狠造成的碰撞，z 修不了，需要地图、路径方面的损失。
- 环岛、灯态未知等"未知"类只能靠运动学。全向停车的到达判定偏紧。
- 多车同时争一个冲突区时，各对的 z 可能互相矛盾（出现环），第一版不处理。

## 8. WM 初版实验计划（2026-11-10；实验 1 已于 2026-11-11 完成，结果见 8.8）

**结论：finetune，不从头训练。** 第一个实验只回答本方案的核心问题：如果 WM 知道每对冲突车谁先过（oracle z，取自日志），碰撞会不会明显下降。WM 本体冻住，只训练一个零初始化的 z→bias 小模块 g。

为什么不从头训练：

- **可归因**：g 零初始化，第 0 步与起点 checkpoint 完全相同，之后的变化只能来自 z。从头训练有 run 间差异：dynbias stage 1 的 ADE −7.6%，碰撞却 +3.6 pt，分不清来源。
- **成本**：从头训练要 stage 1 100k 加 MoN 10k，至少数天；冻结 finetune 单卡几小时。
- **通道已验证**：steering 中 +2 logit 让 ego 只对 2310 等待，两侧都加时碰撞 0.81 → 0.10（第 1 节）。
- 只有实验 1 和 1b 都失败、并且实验 2 表明 WM 表示里没有通行顺序信息时，才考虑从头训练。

### 8.1 小模型实验对本方案的修改

小模型是一维纵向执行层（车沿日志路线走），设置和 WM 不同，但下面几点直接影响 WM 计划：

1. **z 是很强的控制量，但会被盲目执行**（`MATS/waymo_runs/rowz_pilot_20261109/analysis/z_effect.md`）。
   - 碰撞按真值 z < head z < 未知 z 递增（policy 0.6% / 1.3% / 3.0%）。
   - 反转 z 后对方进入时间移动约 1 s（困难样本 1.1–1.7 s），碰撞增加 9–18 pt。
   - 所以 oracle z 实验有意义，同时 head 的校准很关键。
2. **只看当前信息的 z head 可行；给了路线信息后，路权标签没有额外贡献**（`MATS/waymo_runs/rowz_zhead_present_20261109/README.md`）。
   - 只用 1.1 s 历史 + 地图分支 + route head：0.950；告诉它日志对应的地图分支：0.956；只有历史、没有地图：0.915。
   - 在给了日志路线的条件下，加不加路权标签都是约 0.98（0.976 / 0.980）。"只看当前 + 路权"没测过。
   - 所以第一轮不用路权，v5.1 推迟。
3. **同向车对"前车先"一直不释放，会让后车卡住**：pilot 里 11% 的后车没再起步，v2 加了"相距 > 20 m 或 > 2 s 就释放"后降到 0–2%。第一轮 WM 只给交叉和对向车对加 z。
4. **只靠 z 学不会对意外动作的反应**（`rowz_pilot_20261109/analysis/counterfactual_split.md`、`rowz_v2_20261109/analysis/brake_before_flip.md`）。
   - ego 突然抢行时，对方进入时间只推后 0–0.25 s，碰撞 27–35%。v2 每 0.5 s 重估 z 也没改善。
   - z 会翻，但太晚；z 冻住时约 25% 的样本仍会刹车，但几乎都是 ego 车身压到自己路线上之后才刹。
   - 所以实验 1、2 只针对 WM 控制的车之间的协调（80% 碰撞场景的主因：联合 79% vs 打乱 77%）。若 ego 由外部控制（游戏、规划器），必须加 §3.6 的干预训练和明确的让行目标。
5. **回放 ego 时，通行顺序准确率天然约 0.99**，没有参考价值。WM 评估要看闭环碰撞和反事实测试。
6. 小模型里还有三处在 z head 之外用了日志未来路径：决定哪些车对有冲突、按实际进入顺序覆盖 z、同向释放的距离。WM 部署时这些都要换成模型自己的判断（见实验 2 的 3 类 head）。

### 8.2 实验 1（核心）：oracle z，冻结 WM，只训练 g

**起点和数据**（换服务器需要拷贝）：

| 内容 | 路径 | 大小 |
|---|---|---|
| checkpoint（stage 1，step 85000，MoN 之前） | `dreamer4/waymo/checkpoints/waymo_daf_h40_b5_typeaware_vxvy_smarttrajtok_laneconn_scratch100k_20261007/best.pt` | 431 MB |
| 训练和验证数据（含统计文件 `direct_action_stats_typeaware_h40_l11_phys5_yaw075_reexec025_8192_v1.json`） | `dreamer4/data/waymo_vector_dataset_ooi_centered_50k_with_lengths/{train,val}` | 4.6 GB（train 44,998 个样本） |
| map cache | `dreamer4/data/waymo_map_smarttrajtok_5m_v2` | 12 GB |
| lane topology | `dreamer4/data/waymo_lane_connectivity_5m_v1` | 0.5 GB |

**起点 checkpoint 的说明**：

- 它是第 1 节目标模型（MoN `best_ade.pt`）的第一阶段。MoN 的 `config.json` 里写的起点是同目录的 `step_000090000.pt`，这个文件已删除；目录里只剩 `best.pt`（按验证集 flow loss 选出，step 85000，val 0.0764）和 `metrics.jsonl`。所以起点比 MoN 的初始化早 5k 步。mon_select 的两个 run 也是从这个 `best.pt` 开始的。
- 用 `ema_model` 权重：MoN 初始化时加载的是 `ema_model`（`train_waymo_direct_action_flow_mon80.py`），512 评估默认也是 `--weights ema`。
- 这个目录没有 `config.json`，训练参数存在 checkpoint 的 `args` 里（`data_dir`、`val_data_dir`、`map_cache_dir`、`lane_topology_dir`、`action_stats_path` 等）。它们是本机绝对路径，换服务器时要覆盖。
- 选它而不是 MoN 模型的原因：
  - 实验 1 用 stage 1 的 flow loss 训练 g，这正是这个 checkpoint 本身的训练目标；MoN 之后的模型已经被闭环 best-of-8 改过，flow loss 不再是它最后优化的目标。
  - 后面若在 MoN 阶段加 z，有现成的对照：mon_select 的 A run（从同一个 85k `best.pt` 做普通 MoN），`dreamer4/waymo/checkpoints/waymo_daf_laneconn85k_mon8_select_ade_unroll80_b5_detach0_20261106/best_ade.pt`。
- 代价：
  - stage 1 的闭环 ADE 比 MoN 差（见 8.3），rollout 更散，z 的效果可能被噪声冲淡一些。
  - 第 1 节的 probe 和 steering 证据（head 3 负责"等待"、+2 logit 让 ego 只等 2310 等）都是在 MoN 模型上测的，在 stage 1 上不一定完全一样。

**数据格式**：

- 每个样本的 `agents` 是 (32, 91, 8)，列为 x, y, speed, vx, vy, valid, yaw, type，即 32 辆车的完整 9.1 s 日志轨迹，另有 `agent_lengths`。
- 所以 **z 标签直接从样本算**，不需要按 scenario_id 对接审计表，也不需要路权。
- 样本里没有车宽：按类型取默认宽度，取值与评估的碰撞检测一致。

**z 标签**（离线预计算，CPU；每个样本存一组车对记录）：

- **车对**：只做 vehicle–vehicle，两车都要有效。两车日志路径空间重叠（中心距 < 两车半宽之和 + 0.5 m，不要求同时到），且重叠处航向差 ≥ 30°（交叉或对向）。
- **每对存**：i、j、两车各自的进入帧和离开帧（车中心第一次进入、最后离开自己路径上的重叠段），以及交叉角。
- **在训练时刻 t 给标签**（t 是 `select_window_anchors` 选出的窗口起点，范围是第 10–50 帧，所以标签在 batch 里在线算）：

  | t 时刻的状态 | 标签 |
  |---|---|
  | 两车都还没进入 | 日志先后（一辆在日志结束前进入、另一辆没进入，也算进入的那辆先） |
  | 先过的车还在重叠段内 | 它先 |
  | 先过的车已经离开 | 不加 bias |
  | 同帧进入；t 时两车都已在重叠段内；两车在日志结束前都没进入 | 未知，不加 bias |

- 同向车对、非机动车第一轮不加 z。
- 预计算完先统计：每个样本平均有几对标签；按 t 统计各类比例；随机抽 20 对画出来，用肉眼检查。

**z→bias 模块 g**：

- b_ij^h = 3·tanh(MLP(z 的 one-hot, pair 特征))，每个 head 一个数，最后一层零初始化。
- z 未知或没有冲突时 b = 0，此时就是原模型。
- 每对两个方向都算：query i/key j 用 z_ij，query j/key i 用 z_ji，模块共用。
- pair 特征只用当前时刻：j 在 i 坐标系下的相对位置、航向差、距离，以及两车速度。不用冲突区距离这类来自日志未来路径的量，这样实验 2 换成预测的 z 时 g 能原样复用。
- **只加在去噪器 agent_attn 上**，复用 dynbias 的 `chunk_bias` 钩子：
  - 位置是 `dreamer4/waymo/training/world_model/direct_action_flow.py` 中 `JointActionDiTBlock.forward` 的 `relation_bias + scene.chunk_bias`（第 937 行附近，`chunk_bias` 在第 1151 行附近赋值）；
  - 8 层共用，所有 chunk 和 flow 步共用；
  - 编码器和 scene_cross 不加（第 3.2 节）。

**训练**：

- loss 用 stage 1 的 flow loss（`flow_matching_loss`）：日志历史，随机起点，teacher-forced 真值 z。
- WM 全部冻住并用 eval 模式（关 dropout），只更新 g（几万个参数）。
- 单卡 batch 16，lr 约 1e-3，5–10k 步，每 500 步验证一次。stage 1 单卡约 1.3 updates/s，预计 2–3 h。
- 训练中记录：
  - 验证集 flow loss，真值 z 对比未知，看全部车和有标签车对上的车；按"第二辆车的进入帧是否落在 4 s 窗口内"分开；
  - 有标签车对上 bias 的分布（每个 head 的均值，以及 |b| > 3 的比例）。

### 8.3 实验 1 的评估

1. **先重跑基线。** 85k `best.pt` 还没有 512 场景结果。现有的相近结果（同一批 512 场景，每场景 32 个 rollout，闭环 holonomic）：

   | 模型 | ADE | minADE | CPD | 碰撞场景-rollout 率 | offroad |
   |---|---|---|---|---|---|
   | stage 1，step 90000（已删除） | 2.382 | 1.377 | 0.221 | 0.417 | 0.395 |
   | MoN，step 8000 快照 | 1.941 | 1.235 | 0.168 | 0.429 | 0.388 |
   | 日志本身（同一 proxy） | | | | 0.186 | |

   - 出处：stage 1 90k 在 `dreamer4/waymo/eval_results/world_model/mapadapt_laneconn_512_k32_closedloop_holonomic_20261008/laneconn_90k/`，MoN 快照在 `dreamer4/waymo/eval_results/world_model/monbest_512_k32_closedloop_holonomic_20261014/laneconn90k/`。
   - 用新代码路径、z = 未知重跑 85k `best.pt`，并确认与原代码路径在相同种子下输出一致，以此检查钩子。评估参数照 `launch_eval_mapadapt_laneconn_512_tmux.sh`（`--weights ema --focus_mode generate_all`）。
2. **512 场景闭环评估**（`dreamer4/waymo/evaluation/eval_waymo_direct_action_flow_multisample.py`，启动方式同 `launch_eval_monbest_512_tmux.sh`，每场景 32 个 rollout），对比三种 z：
   - **未知**：就是基线。
   - **oracle**：每次重规划（每 5 步）更新。
     - 顺序取日志。
     - 状态取 rollout：先过的车在 rollout 里越过自己重叠段的出口，才释放（把 rollout 位置投影到它的日志路径上判断）。
     - 任一车偏离日志路径超过 2 m 的车对改为未知。
     - rollout 里后车反而先进入时，按实际进入顺序（已在重叠段内的车先）。
   - **反转**：顺序反过来，检验 g 的控制力。
3. **指标**：
   - 碰撞（场景-rollout 率、agent-time 率，同一 proxy），并单独统计有标签车对之间的碰撞；
   - ADE、minADE、CPD、offroad；
   - 冻结车辆比例和"一直不起步"比例；
   - 有标签车对在 rollout 中的通行顺序与日志的一致率。
4. **三个 steering 场景**，用同样的配对种子：95720e9471028705:6062、3a99d1ec2d955550:619、47e836ed96e19bda:1275（工具在 `wm_interaction_probe/`）。原来的数字是 MoN 模型上的，先在 85k 上跑一遍 z = 未知的基线（碰撞率、起步时间）。
5. **`wm_interaction_probe/bias_effect.py`**：确认冲突对上 bias 在 2 logit 左右，不到 4。stage 1 的 head 分工可能和 MoN 模型不同，不要照搬"head 3 = 等待"。
6. **近似第 0 步的分格**：oracle z 消掉的碰撞约等于"顺序没定"类；oracle z 下仍然存在的标签车对碰撞，是"顺序定了但间隔太短"或"路径切得太狠"，再按路径偏离区分这两类。

**判定**：

- oracle 明显降低碰撞（场景配对 bootstrap 显著），冻结和"一直不起步"不上升，ADE 不明显变差：方向成立，进入实验 2。
- 反转 z 能翻转相当一部分标签车对的通行顺序：g 有控制力。
- oracle 几乎不降碰撞：做实验 1b。

### 8.5 实验 2（实验 1 成立之后）：把 oracle z 换成预测的 z

- **先做 A2**：
  - 输入：冻结的 WM 编码器在当前时刻的 agent token，加上与 g 相同的当前 pair 特征。
  - 输出 3 类：i 先、j 先、无冲突。
  - 训练范围：50 m 内所有车辆对，第 10–80 帧中每 5 帧（0.5 s）一个时刻。
  - 标签来自 8.2 的同一份预计算：路径不重叠记为无冲突，先过的车离开后也记为无冲突；同向车对和未知的不计入 loss。
  - 报告准确率、log-loss、ECE，按全部、困难、远（第一辆车进入时间 ≥ 4 s）分开。小模型 C2 的 0.950 只能粗略参照，因为数据和车对定义不同。
- **为什么先做 A2**：在 WM 内部最容易实现，也直接回答"WM 表示里有没有通行顺序信息"。A1（小模型 C2 那样的地图分支特征）工作量大，A2 不够好再做。
- **闭环**：
  - 每次重规划用 head 算 p(z)，每对只采一个、两车共用。
  - 滞回：当前类的概率低于 0.35 才换。
  - 释放由 head 的"无冲突"类负责，不再用日志路径。
  - 对比 未知 / head / oracle。

### 8.8 实验 1 结果（2026-11-11）

**结论**：
- oracle z 没有显著降低碰撞。
- 反转 z 也翻转不了通行顺序，g 没有控制力。
- 按 8.3 的判定应做 1b，但 8.4 原样的 1b 很可能同样失败。原因是 z 覆盖的车对太少、信号太弱（见 8.8.6），修改建议见 8.8.7。

#### 8.8.1 实际做法

- 代码在 `dreamer4/waymo/pair_order_z/`，运行目录是 `dreamer4/waymo/pair_order_z/runs/exp1_oracle_z_frozen_20261110/`。
- 各步骤对应的代码：

  | 步骤 | 代码 |
  |---|---|
  | 标签 | `make_z_labels.py` |
  | g 模块和按时刻给标签 | `z_bias.py` |
  | 训练 | `train_zbias_frozen.py` |
  | 评估 | `eval_zbias.py`，包住原 `eval_waymo_direct_action_flow_multisample.py`，原文件不改 |
  | 汇总 | `summarize_exp1.py` |
  | 流水线 | `run_exp1.sh` |

- 运行目录里的输出：`summary.md` 是汇总，`pair_diag.txt`、`bias_magnitude.json`、`collision_breakdown_unknown.json` 是后面三项诊断的结果。
- 标签（vehicle–vehicle、交叉或对向、按 8.2 的规则）：

  | 范围 | 车对 | 样本 / 场景 |
  |---|---|---|
  | train | 17,231 | 10,322 个样本 |
  | val | 1,825 | 1,075 个样本 |
  | 512 个评估场景 | 193 | 115 个场景 |

- 训练：
  - g 是 MLP 9→128→128→8，零初始化，1.9 万个参数。
  - batch 16，lr 1e-3，8000 步，约 57 分钟。
  - 按 val_all_loss_z 选出 step 1500。它在让行车和有标签车上的增益也是最好的。
- 闭环 oracle：
  - 每次重规划都按 rollout 状态重算 z：把车的位置投影到它自己的日志路径上。
  - 任一车偏离日志路径超过 2 m，这对车改为未知。
  - reversed 模式只把顺序反过来，其余不变。
- 与计划不同的地方：
  - 训练时 SDPA 强制用 math kernel。默认的 memory-efficient kernel 反传时报 "LSE is not correctly aligned"。评估仍用默认 kernel。
  - 计划里的"|b| > 3 的比例"在 3·tanh 下恒为 0，改报"任一 head |b| > 2.5"。
  - 本机 map cache 的 `source_npz` 存的是 `/p/yufeng` 路径，由 `compat.py` 在运行时修补身份检查，仓库文件没有改。
- 钩子检查：g 输出全 0 时，评估结果与原代码路径逐位相同（在有车对的 batch 18 上验证）。
- 耗时：一次 512 × 32 评估单独占卡约 80 s/batch，共 128 个 batch，约 2.9 h。卡已经跑满，三个评估并行时总吞吐不增加；和训练同时跑时，评估会慢约 3 倍。

#### 8.8.2 训练：验证集 flow loss，真值 z 相对"未知"的下降

| step | 全部车 | 有标签车 | 让行车 | 优先车 | 后车 4 s 内进入 | 后车 4 s 后进入 |
|---|---|---|---|---|---|---|

#### 8.8.4 诊断

**z 确实改变了车对的轨迹，但变化不分方向**（`pair_diag_exp1.py`，193 对 × 32 次，与 unknown 逐条配对比较）：

- 8 s 时与 unknown 的位置差：

  | 车 | oracle | reversed |
  |---|---|---|
  | 让行车 | 1.17 m | 0.94 m |
  | 同场景的其他车 | 0.07 m | 0.06 m |

  说明钩子生效了。
- 两种模式下都是优先车多走一点（8 s 时 oracle +0.26 m，reversed +0.29 m），让行车基本不变。
- 通行顺序的结果只有 2.5% 发生了变化。日志顺序变反序 8 次，反序变日志顺序也是 8 次。变化多数是"没相遇 → 按日志顺序"（73 次），只是车多走了一点。
- 结论：g 学到的是"这两辆车在交互"，不是"谁先过"。

**bias 不小，attention 也被改了，行为却不跟方向走**（`bias_magnitude.py`，960 个验证样本，训练时的状态）：

| 量 | 让行边（让行车 → 优先车） | 优先边 |
|---|---|---|
| 每个 head 的 \|b\|，平均 / 中位 | 1.96 / 2.22 | 1.07 / 1.00 |
| 每条边 8 个 head 中最大 \|b\| 的平均值 | 2.90（几乎都顶在上限 3） | 2.02 |
| 随方向变化的部分 \|b(z) − b(反转 z)\|，平均 | 0.81 | 0.95 |
| 不随方向变化的部分 | 1.61 | 1.27 |
| 对照：同一条边上 WM 自己的 relative bias，平均（中位） | 0.82（0.42） | 0.82（0.41） |
| 对照：logit 在各 key 之间的标准差，中位 | 1.41 | 1.34 |
| attention 权重中位数：无 z / oracle / reversed | 0.016 / 0.003 / 0.007 | 0.017 / 0.012 / 0.005 |

- 让行边的 bias 在 8 个 head 里有 6 个为负（−0.7 到 −2.9），head 3 为 +2.4，head 6 约为 0。也就是让行车整体更少看优先车，和 steering 里有效的 +δ 方向相反。不过 stage 1 和 MoN 的 head 分工不一定相同。
- 所以瓶颈不在 bias 的大小，放大上限大概率没用。冻结的 WM 不会把这种 attention 变化读成"等"还是"走"。

#### 8.8.6 为什么只有很少一部分车对用到了 z

一句话：z 只定义给日志里真正交叉的车对，这样的车对很少；有 z 的车对也只在冲突发生前那一段时间有 z；而训练时它又被其他车的 loss 稀释，加上模型本来就能猜对大部分顺序。三层叠在一起，模型几乎没有机会学会用 z。

1. **大部分车对根本没有 z。** 8.2 只给"日志路径交叉或对向、且不是一开始就在重叠段里"的机动车对定义 z。

   | 筛选 | train | val |
   |---|---|---|
   | 日志路径有空间重叠的机动车对 | 428,218 | 49,920 |
   | − 同向（航向差 < 30°，第一轮不做，见 8.1 第 3 点、8.6） | −402,189（94%） | −47,293 |
   | − 第 5 帧前已在重叠段（pre_existing） | −8,798 | −802 |
   | − 同帧进入（tie） | −9 | −3 |
   | **保留，有 z** | **17,231（4.0%）** | **1,825（3.7%）** |

   - 平均每个样本 0.38 对。77% 的训练样本一对都没有：44,998 个里只有 10,322 个有。
   - 每个样本最多 32 个 agent，其中平均约 22 辆机动车，有 z 的平均不到 1 对。
   - 行人和自行车这一轮也不做。

2. **有标签的车对，也只在一段时间里有 z。**
   - z 只在"谁先过还没发生"时开着：两车都还没进入，或者先过的车还在重叠段里。
   - 先过的车离开后就释放，bias 归 0。
   - 闭环里任一车偏离日志路径超过 2 m，日志顺序不再适用，改为未知。
   - 512 场景 oracle 评估中，有标签车对在各次重规划中的状态比例：

     | 状态 | 比例 |
     |---|---|
     | 都还没进入 | 26.1% |
     | 先过的车在重叠段里 | 9.3% |
     | 已释放 | 34.5% |
     | 偏离日志路径 | 27.7% |
     | 其他 | 2.4% |

     真正带着 z 的只有约 36%。
   - 训练时的随机窗口起点（第 10–50 帧）上，有标签车对约 59% 处于 z 开着的状态。

3. **训练信号被稀释，而且 z 大多是多余信息。**
   - 训练只用了有车对的样本，但 loss 仍对场景里所有车计算。在 960 个验证样本中，有 z 的车只占 agent-步的 9.5%（63,550 / 672,074）。
   - 模型不看 z，也能从场景推断出大部分顺序：有冲突时 84% 按日志顺序通过。z 只在剩下的少数情况里提供新信息。
   - 结果是全部车的 flow loss 只降了 0.085%，让行车降了 0.86%。g 只学到了不分方向的那部分 bias（见 8.8.4）。

#### 8.8.7 下一步（建议，尚未与用户确认）

- **8.4 原样的 1b 只解决了"冻结的 WM 读不懂 bias"这一个问题**，没有解决 8.8.6 的稀疏和稀释，大概率同样失败。建议把 1b 改成测 z 能力的版本：
  1. **标签 v2，扩大覆盖面：**
     - 加入同向车对（并道、变道、跟车），按"谁先进入共用路段"定 z，覆盖面约扩大一个数量级。同向车辆也是最大的碰撞来源。
     - 一开始就在重叠段的车对也保留，已经在里面的车先过。
     - "已释放"作为一个显式的 z 状态，而不是 bias 归 0。
     - 同向车对要带上 8.1 第 3 点的释放规则：相距 > 20 m 或 > 2 s 就释放。
     - 行人和自行车下一步再加。
  2. **训练窗口只取 z 正在起作用的时刻**：窗口起点时至少一对车还没通过冲突区，并且后车在 4 s 内进入。
  3. **loss 集中在有 z 的车上**：只算这些车，或者大幅加权。
  4. **解冻去噪器**：lr 1e-5（1e-6 可能学不出新用法），和 g 一起训练，z-dropout 0.3。
  5. **评估**：
     - z 基准集：验证集所有有标签车对，从进入冲突区之前开始，分别跑 unknown / oracle / reversed。
     - 指标：通行顺序跟随 z 的比例（reversed 能翻转多少，就是控制力）、车对碰撞率、ADE。
     - 另跑一遍 512 场景的 unknown 模式，检查解冻后模型本身没有退化。
- **判定：**
  - reversed 能翻转相当比例的顺序：z 能控制 WM 的交互行为，进入实验 2。
  - z 密集、loss 集中、去噪器解冻之后仍不能翻转：放弃"agent_attn bias"这个通道，改为 z token 或 FiLM 输入，或考虑从头训练。
- **从头训练暂不可行：** stage 1 是 4 卡、有效 batch 16、1.34 steps/s 跑 100k 步，约 21 h。换到单张 A40 约 3–4 天，超过当前 SLURM job 的剩余时间（11-13 11:54 结束）。
